# GameGuy 产品需求与实施方案

- 版本：v0.1（立项与技术评审草案）
- 日期：2026-10-22
- 产品形态：基于 DeepSeek Harness（DSH）的本地优先游戏 Agent 平台
- 首期建议：Minecraft 自主任务 + 明日方舟日常自动化
- 文档状态：范围、指标与排期为建议值，尚未通过原型或实际测试验证

## 1. 项目摘要

GameGuy 让用户通过自然语言连接游戏、委托任务、查看进度，并在需要时暂停或接管。平台复用 DSH 的模型、Agent、工具、会话和基础 UI，以插件方式接入不同游戏及其自动化后端。

首期不追求“一个模型玩所有游戏”，而是验证两种互补模式：

1. **自主玩法模式**：Agent 做目标分解与规划，游戏控制器执行高频动作，适用于 Minecraft 等开放环境。
2. **可靠自动化模式**：成熟自动化后端执行确定性流程，Agent 负责配置、任务组织和异常解释，适用于二游日常。

核心价值不是聊天入口，而是把游戏后端封装为**可观察、可取消、可验证、可人工接管**的能力。

## 2. 背景与问题

现有游戏自动化方案通常只服务单个游戏，连接方式、任务配置、日志与异常处理各不相同。通用 Agent 则缺少游戏状态模型、连续操作控制和任务成功核验。

用户需要解决的问题：

- 不想记住每个自动化工具的配置与操作入口。
- 希望用目标而不是底层动作描述需求，例如“收集木头做一把石镐”。
- 希望知道任务为什么失败、实际完成了什么，而不是只看到程序正常退出。
- 希望随时停止自动操作，避免误用资源或与人工操作冲突。

开发者需要解决的问题：

- 接入新游戏时，不重复实现模型调用、会话和 UI。
- 复用现有驱动、识别资源和自动化流程，而不是重新造轮子。
- 有明确的插件契约、兼容性检查和测试方法。

## 3. 产品定位与目标用户

### 3.1 产品定位

**GameGuy = DSH 游戏专用组合配置 + 游戏能力协议 + 可信游戏插件。**

首期面向本地运行，用户自行提供游戏客户端、合法账号与模型配置。GameGuy 不提供游戏账号、商业游戏安装包或云端代登录服务。

### 3.2 目标用户

| 用户 | 主要诉求 | 首期优先级 |
|---|---|---|
| 游戏 Agent 爱好者 | 用自然语言委托沙盒游戏任务并观察执行 | 高 |
| 已使用自动化工具的玩家 | 统一组织日常流程，查看完成项与错误 | 高 |
| 插件开发者 | 快速包装已有游戏后端 | 高 |
| 普通零技术玩家 | 一键安装、零配置使用 | 后续 |
| 游戏研究团队 | 多 Agent 协作、实验评测 | 后续 |

### 3.3 首期目标

- 一个平台通过同一插件协议接入两类差异明显的后端。
- 用户可以连接、委托、观察、取消、核验和接管任务。
- 在不修改 DSH Agent loop 的前提下完成接入。
- 每个任务有明确状态、结构化结果和成功证据。
- 不同对话不能同时争夺同一个受控角色或设备。

### 3.4 首期非目标

- 任意游戏零适配接入。
- FPS、动作游戏的逐帧视觉决策与竞技对战。
- 通用视觉模型替代全部 OCR、寻路和自动化流程。
- 云端账号托管、多租户商业服务或开放插件市场。
- 多 Agent 协作、自动生成并直接执行任意游戏脚本。
- 自动付费、抽卡、资源交易、账号切换与绕过反作弊。
- 保证商业游戏自动化不被封号。
- 进程退出后的自动续跑与 24/7 无人值守调度。

## 4. 范围与产品阶段

优先级定义：P0 为首期必须完成；P1 为首期验证后建设；P2 为扩展探索。

| 能力 | 优先级 | 说明 |
|---|---|---|
| DSH 外部 bundle 与插件注册 | P0 | 固定支持版本，不先 fork 内核 |
| Minecraft 驱动 | P0 | Mineflayer，对接用户指定测试服务器 |
| 明日方舟日常驱动 | P0 | MAA，先支持一个固定客户端与连接方案 |
| 游戏实例、任务状态、控制权 | P0 | 明确绑定对话、实例与任务 |
| 观察、技能执行、取消、验证 | P0 | 形成闭环 |
| 基础任务展示与人工接管 | P0 | 先复用 DSH 工具卡片与命令 |
| 插件兼容性与契约测试 | P0 | 提供参考插件和测试夹具 |
| 专属游戏面板 | P1 | 游戏列表、截图、结构化进度与历史 |
| 持久化计划、日程与重启核对 | P1 | 独立于当前进程内 jobs 建设 |
| MaaFramework 资源型插件 | P1 | 核心契约验证后扩大二游覆盖 |
| Factorio 等第三类游戏 | P2 | 评估是否需要新的能力扩展 |
| 多 Agent、技能共享、插件市场 | P2 | 可靠性与信任治理成熟后建设 |

首期 Minecraft 与 MAA 先后推进，不要求两个后端同时开工。以 Minecraft 作为协议与生命周期的参考实现，再用 MAA 检验协议是否过度偏向沙盒游戏。

## 5. 核心用户流程

### 5.1 Minecraft 自主任务

1. 用户选择 Minecraft 插件并配置服务器、版本与机器人连接信息。
2. 平台连接游戏，报告位置、生命值、背包和可用技能。
3. 用户输入：“收集 16 个原木，做出一把石镐。”
4. Agent 检查目标可行性、环境和权限，形成任务计划。
5. Agent 调用采集、移动和合成等高层技能；Mineflayer 执行寻路与即时动作。
6. 平台记录进度，必要时重新观察并调整计划。
7. 根据背包和状态核验目标，返回实际完成量与失败原因。
8. 用户可随时暂停或接管。测试范围应限定在已知资源可达的受控世界。

### 5.2 明日方舟日常

1. 用户自行登录游戏，配置 MAA 支持的连接端点。
2. 平台预检查连接、客户端状态与支持的任务。
3. 用户输入：“按我的日常清单执行，不使用源石，不自动购买。”
4. 平台展示计划与资源策略；MAA 执行已有任务流程。
5. 将后端进度与完成证据转换为结构化事件。
6. 对未知页面、证据不足或任务中断，停止或按白名单规则恢复。
7. 返回完成、失败、未执行的任务清单。不能根据后端退出码直接宣布全部成功。

首期应选择 MAA 已支持且可核验的领取、基建、指定关卡等流程；具体任务名单需在集成原型中确认。不承诺完成任意自然语言描述的日常操作。

### 5.3 异常与接管

1. 出现断线、未知页面、低置信度识别或高风险操作。
2. 平台停止新动作，尝试停止当前后端操作，展示停止是否确认。
3. 用户人工处理后点击“重新观察”。
4. 平台核对状态，再允许继续；不能直接沿用异常前的观察结果。

## 6. 功能需求

### FR-01 游戏插件与配置（P0）

- 支持可信插件的安装、启用、禁用和配置校验。
- 记录插件版本、后端版本、支持的游戏版本、平台和能力列表。
- 缺少依赖或版本不兼容时拒绝连接，并给出可执行的修复提示。
- 插件配置与账号秘密分开存储；日志、工具参数和模型上下文不得包含密码或令牌。
- Agent 不得默认安装、更新或修改插件。插件管理由用户或明确授权流程触发。
- 卸载与更新前需停止任务、释放控制权并断开驱动；首期不支持执行中的热切换。

**验收**：不兼容插件不能进入可执行状态；卸载后不留下持续游戏动作或未报告的运行后端。

### FR-02 游戏实例与连接（P0）

- 创建、连接、断开和查询游戏实例。
- 为受控资源分配稳定身份：Minecraft 角色、设备连接或游戏窗口。
- 状态至少包含未连接、连接中、就绪、执行中、暂停、异常、断开。
- 连接成功后获取能力清单和初始观察。
- 首期单次任务只绑定一个游戏实例，不支持跨游戏组合目标。

**验收**：断线后不能继续基于旧连接执行；重连必须重新观察并核对状态。

### FR-03 结构化观察（P0）

- 通用字段包含时间、来源、实例身份、观察版本与有效性。
- Minecraft 保留位置、生命值、背包、附近实体与相关世界信息。
- 二游保留页面识别、流程节点、任务进度与必要的截图引用。
- 所有影响模型判断的观察应通过工具结果或会话事件留痕，可按记录解释当时的决策。
- 截图以按需采集为主，不默认持续录屏；可配置保存期限并删除历史文件。

**验收**：过期观察不得直接授权高风险动作；任务结果可追溯到对应观察或后端证据。

### FR-04 任务委托与策略约束（P0）

- 支持自然语言目标转为可执行计划，说明支持范围与无法完成的部分。
- 附带执行时限、模型预算、允许技能和资源使用策略。
- 任务需要记录用户目标、实例、执行者、计划和结果。
- 高风险规则在 runtime 中强制执行，不能仅写在提示词中。
- 对超出能力范围的请求，明确拒绝或要求补充配置，不凭空生成操作。

**验收**：禁止源石消耗等策略在模型错误调用时仍生效；达到时限或预算后停止新规划与新动作。

### FR-05 技能执行与后台任务（P0）

- 提供游戏专属强类型工具，不使用无约束的通用 action RPC 作为主要接口。
- 每个技能声明参数、前置条件、风险、超时、取消能力、重试语义与验证方式。
- 长任务复用 DSH jobs，返回任务标识并报告进度。
- 游戏实时控制交给本地后端；模型不参与逐帧控制。
- 执行参数、后端报告与验证结果分开记录。
- 同一受控资源的改变状态操作串行化；只读观察是否可并行由后端声明。

**验收**：长任务不会阻塞用户发出取消命令；后端正常退出但验证失败时不能返回目标成功。

### FR-06 结果核验（P0）

- 通用核验结果至少区分：已验证成功、部分完成、已验证未达成、无法确认。
- Minecraft 优先使用背包数量、位置和物品状态验证。
- 二游优先使用可信后端任务回报，并补充可用的页面或资源状态证据。
- 任务运行状态与目标结果分开。例如 job completed 只表示执行结束。
- 最终报告列出完成项、未完成项、证据、错误与建议，不隐藏验证缺口。

**验收**：识别失败、断线或缺少证据时报告“无法确认”，不误报成功。

### FR-07 取消、暂停与人工接管（P0）

- 提供不依赖新模型回合的停止入口，可用命令或基础 UI。
- 暂停首先停止派发新动作；是否能中断正在执行的技能必须由驱动报告。
- 取消需等待后端停止确认；不能用任务卡片变灰代替停止证明。
- 人工接管后，Agent 不得继续发送改变游戏状态的动作。
- 只有确认旧执行者停止或被隔离，才能授予新的控制权。
- 无法停止时进入“停止未确认”状态，提示用户在后端或客户端手动停止。

**验收**：暂停、取消、停止未确认在界面和事件中可区分；接管之后没有旧 Agent 的新动作。

### FR-08 控制权与会话隔离（P0）

- 区分 Agent Session、Game Session 和 Job，维护绑定关系。
- 同一角色、窗口或设备仅有一个改变状态操作的控制者。
- 不同 Agent Session 争用资源时明确拒绝或等待，不静默抢占。
- 控制权应包含所有者和代次标识，避免过期执行者继续发送动作。
- 锁失效不意味着旧后端已经停止；重新分配前必须核对执行状态。

**验收**：两个对话同时操作同一设备时只有一个成功取得控制权；对不同资源可独立执行。

### FR-09 异常处理与重试（P0）

- 错误分类包括连接、前置条件、识别、能力不足、策略拒绝、超时、取消与后端故障。
- 自动重试仅限已声明安全、次数有界的操作。
- 改变资源的操作发生超时后先观察核对，不得直接再次执行。
- 请求标识用于去重和追踪，但不承诺端到端 exactly-once；不同后端对幂等的支持需明确声明。
- 默认禁止未知页面下盲点、无限重试或失败后自动执行任意脚本。

**验收**：注入“动作已生效但响应丢失”场景，不产生未经核对的重复资源消耗。

### FR-10 执行展示与历史（P0 / P1）

- P0 展示连接状态、当前任务、阶段进度、最终报告和停止入口。
- P0 优先复用 DSH 通用工具卡片、任务输出与用户命令。
- P1 通过 Client 插件提供游戏实例列表、截图、任务清单和接管按钮。
- 历史记录允许排查决策和工具结果，不承诺重放能够还原外部游戏世界。
- 清晰展示后端失败和模型失败，便于定位责任层。

**验收**：用户能看到任务是否仍在运行、是否停止确认以及目标是否核验成功。

## 7. 技术方案

### 7.1 DSH 集成方式

采用外部 GameGuy bundle 接入现有 DSH profile。原型阶段以配置 patch 挂载，后续发布命名的 GameGuy profile。每个游戏通过 Agent preset 选择自己的工具与提示词，不把 profile 级启用等同于会话隔离。

| DSH 能力 | 使用方式 |
|---|---|
| tools | 注册游戏工具与参数 schema |
| systemPrompt / agentPresets | 组织游戏规则、可用工具与玩法说明 |
| sessions | 记录模型可见观察、工具结果与任务事件 |
| jobs | 当前进程中的长任务、进度与取消入口 |
| subprocess | 启动、监控和停止外部后端 |
| approval | 需要用户确认的高风险操作 |
| commands | 不通过模型回合执行暂停、停止等命令 |
| Client 插件 | 后续实现游戏专属面板 |

不直接依赖具体 Agent loop 实现。通过契约与服务对接，并集中维护 DSH 兼容桥接层。

### 7.2 GameGuy 模块职责

- **game-contract**：实例、能力、观察、任务、错误、结果与生命周期的类型定义。
- **game-runtime**：驱动注册、连接、控制权、策略校验、任务协调与事件转换。
- **provider-minecraft**：Mineflayer 连接、状态读取与高层技能。
- **provider-maa**：MAA 桥接、任务参数校验、进度转换与核验。
- **tool-game**：模型可见工具与用户命令。
- **bundle / presets**：安装组合、默认工具集与权限配置。
- **ui-game（后续）**：消费持久化事件和结果元数据，提供专属展示。

可先放在同一仓库，契约保持独立；不因架构图而提前拆出大量部署单元。

### 7.3 插件协议草案

以下为待实现的 GameGuy 契约，并非 DSH 内置 API。

| 方法 | 职责 | 要求 |
|---|---|---|
| describeCapabilities | 获取支持能力与限制 | 包含平台、版本、技能、风险与取消语义 |
| connect | 建立游戏连接 | 预检查、身份确认、限时 |
| observe | 获取结构化观察 | 保留来源、时间、版本与未知字段 |
| startSkill | 执行高层技能 | 携带实例、控制代次、请求标识、策略与截止时间 |
| getTaskStatus | 查询任务 | 明确是否实际运行、是否停止确认 |
| cancelTask | 请求停止 | 返回停止确认或无法确认，不隐藏延迟 |
| verify | 核验目标或技能结果 | 可返回部分完成和无法确认 |
| disconnect | 释放连接 | 执行中不得无提示直接卸载 |

驱动不需要支持所有高级能力，但必须显式声明缺失能力。若无法提供取消或安全停止，首期不允许作为无人值守的改变状态插件接入。

### 7.4 最小数据模型

| 对象 | 关键字段 |
|---|---|
| PluginManifest | 插件与协议版本、支持的 DSH / 游戏 / 后端版本、平台、权限、能力 |
| GameInstance | 实例标识、插件、受控资源标识、连接状态、配置引用 |
| ControlLease | 所有者、资源标识、控制代次、有效期、停止核对状态 |
| Observation | 时间、来源、观察版本、状态数据、证据引用、有效性 |
| GameTask | 用户目标、Agent Session、Game Session、Job、计划、策略、状态 |
| SkillExecution | 请求标识、技能参数、开始结束时间、后端结果、取消与重试记录 |
| Verification | 目标、核验结论、实际完成量、证据、未知项 |

凭据只保存安全引用，不作为这些对象的可展示字段。

### 7.5 生命周期与恢复

任务主流程：待执行 → 预检查 → 执行中 → 核验中 → 成功 / 部分完成 / 失败 / 无法确认。

暂停、取消中、已取消与停止未确认作为独立状态处理。发生进程退出后，记录为中断或待核对，不自动标记失败或成功；下次启动重新读取游戏状态。

当前 DSH jobs-local 是进程内实现，不能作为持久调度器。P1 的无人值守方案必须单独设计持久计划、外部执行身份、检查点、启动后 reconciliation 和重复执行防护。

## 8. 非功能需求与安全边界

### 8.1 运行环境

- 首期以 Windows 11 本地运行作为验收环境，其他系统不作为首期承诺。
- DSH 使用其支持的 Node 版本，并固定经过测试的具体版本组合。
- Minecraft 游戏与服务器版本、MAA 版本及连接方案在测试矩阵中锁定。
- 原型阶段先验证 DSH 与两个后端在目标环境可运行，再承诺一键安装。

### 8.2 性能与成本

- 模型只处理计划、低频观察和异常，不参与逐帧控制。
- 观察内容按任务裁剪，不将全部日志与截图持续塞入上下文。
- 每个任务记录模型调用次数、token 与可获得的费用估算；不同模型价格单独配置。
- 确定性日常任务的正常流程不需要视觉模型逐步判断。

### 8.3 安全与隐私

- Host 插件属于可信代码，运行于 DSH 主进程；工作区 sandbox 不等于插件安全沙箱。
- 外部后端放入子进程用于故障与生命周期隔离，不宣称由此实现完整安全隔离。
- 推荐专用测试环境或虚拟机，插件来源采用白名单。
- 默认禁止购买、抽卡、稀有资源消耗、账号变更与危险删除；未来开放需独立策略与审批。
- 游戏聊天、OCR、网页与日志属于不可信输入，不能改变权限、诱导安装插件或执行任意代码。
- 不默认上传完整屏幕、秘密或无关窗口；使用云模型时明确告知实际上传的观察或截图范围。
- 商业游戏需评估服务条款、许可证和封号风险，不支持绕过安全与反作弊机制。
- DSH 的 MIT 许可不替代 Mineflayer、MAA、资源包及其他依赖的许可审查。

### 8.4 可维护性

- 插件声明协议与依赖版本，发布时提供兼容矩阵。
- 核心 runtime 单元测试 + 驱动契约测试 + 真实游戏集成测试分层维护。
- 不把真实账号信息和游戏秘密写入测试夹具。
- 更新游戏版本后先做 smoke test，未验证版本标记为未知支持，而不是默认兼容。

## 9. 首期验收指标

以下为建议的发布门槛，不代表当前已经达到。质量指标仅适用于约定测试环境，不外推到任意世界、账号或客户端。

| 指标 | 建议门槛 | 测量方式 |
|---|---|---|
| 架构可插拔 | 两个后端均无需修改 DSH Agent loop | 代码评审与集成测试 |
| 控制冲突 | 20 次同资源争用测试，零双控制者 | 并发请求与动作记录 |
| 禁止资源操作 | 20 次策略拒绝测试，零实际禁用动作 | runtime 测试与后端记录 |
| Minecraft 任务成功率 | 受控世界中 20 次运行至少 18 次核验成功 | 固定资源布局与目标集合 |
| 日常任务成功率 | 固定支持流程 20 次运行至少 19 次核验成功 | 已登录、正常网络、固定版本 |
| 成功误报 | 验收样本和故障注入中为零 | 对照真实游戏状态人工复核 |
| 停止新动作 | 取消入口触发后 1 秒内停止派发 | 本地事件时间戳 |
| 当前动作停止 | 可取消技能目标 5 秒内确认；超时明确报告 | 驱动取消测试 |
| 异常覆盖 | 断线、未知页面、响应丢失、崩溃、超时均有明确结果 | 故障注入矩阵 |
| 执行可追溯 | 所有终态都有结果、核验结论和证据或缺口说明 | 事件记录检查 |

20 次运行只作为 MVP 门槛，不能证明生产级可靠性。延迟门槛需在原型阶段按后端真实能力校准；不可中断的技能必须明确展示限制。

## 10. 测试方案

1. **契约测试**：插件能力声明、参数校验、生命周期、错误与取消语义。
2. **策略测试**：模型绕过参数、禁止资源使用、过期观察和不可信游戏文本。
3. **并发测试**：两个对话争用同设备、旧控制代次失效、接管后旧请求抵达。
4. **故障注入**：网络断开、后端退出、动作成功响应丢失、截图无法识别、任务超时。
5. **集成测试**：受控 Minecraft 世界与专用 MAA 测试配置，人工复核结果。
6. **升级测试**：固定 DSH、插件、游戏与后端版本的兼容矩阵。
7. **退出清理测试**：插件禁用、正常退出和异常退出后，检查残留进程与持续动作。

禁止通过真实付费、抽卡或不可逆资源消耗验证安全能力；采用 mock 或安全测试环境。

## 11. 实施计划与交付物

建议配置：2 名研发（平台与驱动），测试支持兼职。预计 6–8 周形成可评审 MVP，前提是复用成熟后端、不重写识别流程；以下是估算而非交付承诺。

| 阶段 | 估算 | 工作 | 交付物 / 退出条件 |
|---|---|---|---|
| M0 技术原型 | 1 周 | 固定 DSH 版本；打通两种连接、工具调用与取消 | 兼容矩阵、可行性结论；取消不可控需降级范围 |
| M1 平台骨架 | 1–2 周 | 契约、实例、控制权、策略、事件与 jobs 桥接 | 参考插件、契约测试、基础任务流程 |
| M2 Minecraft | 1–2 周 | 观察、移动、采集、合成与核验 | 受控世界任务集及成功率报告 |
| M3 MAA 日常 | 1–2 周 | 固定任务集、进度、策略与完成核验 | 日常清单、连接指南、故障测试 |
| M4 联调发布 | 1 周 | 停止与接管、故障矩阵、安装说明和许可检查 | MVP 包、测试报告、演示与已知限制 |

MVP 交付清单：GameGuy bundle、两个可信驱动、游戏 presets、插件开发指南、参考插件、验收脚本、兼容矩阵、安全与隐私说明、演示流程。

P1 的专属 UI、持久日程和重启恢复单独排期，不挤入首期验收。

## 12. 主要风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| DSH API 变化 | 插件失效、升级成本 | 固定版本，桥接层集中依赖，契约测试 |
| 游戏与客户端更新 | 识别或动作语义失效 | 白名单版本、更新 smoke test、未知状态停止 |
| 后端不能及时取消 | 人工接管冲突、持续操作 | 先验证取消能力；未确认停止不转移控制权 |
| 假成功与不安全重试 | 用户误判、重复消耗资源 | 单独核验、未知态、观察后重试 |
| 插件执行权限过大 | 主机安全风险 | 可信来源、最小权限、专用环境，不开放任意安装 |
| 账号与自动化规则 | 封号及运营风险 | 本地优先、使用规则评估、明确风险，不做规避 |
| 泛化承诺过大 | 范围失控 | 固定两款游戏和有限技能，第三款以后验证 |
| 依赖与资源许可 | 分发限制 | 逐项审查，必要时由用户自行安装后端 |

## 13. 评审前需要确认的决策

当前草案采用以下默认假设，评审时确认即可，不阻塞原型：

1. 首期二游选择明日方舟 + MAA，而不是直接承诺所有二游。
2. 首期 Windows 11 本地部署，用户自行登录，平台不保存账号密码。
3. 原型先挂载 DSH Web profile，首期不 fork 内核，也不重做整套 UI。
4. Minecraft 限定已验证版本与测试服务器，不承诺公共服通用可用。
5. 稀有资源消耗与购买默认禁止，首期不开放审批后购买能力。
6. 自动日程与崩溃续跑归入 P1，MVP 只支持当前运行进程内的委托。
7. 确认支持的模型、费用预算、日志与截图默认保存期限。

## 14. 后续扩展原则

- 新游戏必须通过同一生命周期、控制权和安全测试，再接入工具层。
- 有官方或成熟结构化接口时优先使用，不优先选择纯视觉点击。
- MaaFramework 类插件区分“执行引擎”和“游戏资源包”，分别管理版本、来源与兼容性。
- 第三类游戏用于验证契约泛化，不为了统一而丢弃游戏特有状态。
- 插件市场开放之前，先建设签名、来源、权限展示、更新审核与安全治理。
- 多 Agent 场景必须先明确角色和资源控制边界，不以多对话并发替代协作机制。
