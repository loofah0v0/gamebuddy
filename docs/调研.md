有，而且现在已经形成了几条比较清晰的路线。**但“让 agent 玩游戏”要分成三类：原生 LLM 玩家、给 agent 用的游戏控制接口，以及可以被 agent 调度的日常脚本。** 这三类的能力和落地成本差别很大。

我按你提到的 **MC 自主玩游戏**、**二游自动收菜** 两个方向，核查了 GitHub 仓库的 README、文档和部分 Release 页面。以下截至 **2026 年 10 月 22 日**，未逐项实机测试。

## 先给结论

最值得优先看的项目是：

| 你的目标 | 优先看 | 原因 |
|---|---|---|
| 尽快体验“LLM 自己玩 MC” | **Mindcraft** | 已把模型、Mineflayer、行动技能接起来 |
| 让自己的 agent 接管 MC | **minecraft-mcp-server** | 通过 MCP 暴露游戏操作，不必从协议层开始 |
| 让现有 agent 操作二游界面 | **MaaMCP** | 提供截图、OCR、点击及可复用流程，是最贴近这个需求的桥梁 |
| 用 coding agent／命令行调游戏自动化 | **maafw-cli** | CLI＋AI skill，适合命令调用，但仍是实验性项目 |
| 稳定完成二游日常 | **MAA、BetterGI、各类一条龙＋薄封装** | 已有成熟流程，通常比 LLM 每一步看图点击可靠 |
| 研究长程规划、生产链 | **Factorio Learning Environment** | 专门为 LLM agent 玩异星工厂设计 |
| 研究“仅靠画面和键鼠玩游戏” | **Cradle** | 有多个商业游戏的视觉控制适配，但研究属性较强 |

## 一、Minecraft：最完整的 agent 玩游戏生态

### 1. [Mineflayer](https://github.com/PrismarineJS/mineflayer)：控制底座，不是 LLM 本身

这是你提到的路线，也是目前很适合自己搭 agent 的底座。

- 面向 **Minecraft Java 版**。
- 通过游戏协议获取结构化状态：方块、实体、背包、位置等。
- 提供移动、挖掘、放置、合成、聊天等高层 API。
- 以 JavaScript／Node.js 为主，有寻路、采集、战斗等插件生态。

**优势：** 不必让模型从截图里判断每个方块，观察和动作都比较明确。

**边界：** 它只提供“身体”，任务规划、记忆、模型调用和失败恢复需要你自己接。

适合架构：

> LLM 决定“收集木材并造工作台” → 技能层拆解 → Mineflayer＋寻路插件执行。

### 2. [Mindcraft](https://github.com/mindcraft-bots/mindcraft)：更接近现成的 LLM 玩家

基于 Mineflayer，已经包含模型接入、聊天交互、行动技能等，可以做任务和多 agent 互动，也支持多家模型及本地模型服务。

**推荐度最高的场景：** 你想先看看“agent 自主玩 MC”究竟能做到什么，而不是先开发整套框架。

需要注意：它可以允许模型生成并执行技能代码，相关不安全编码开关默认关闭。**不要为了方便在公网服务器上随意开启**，游戏内聊天等外部输入也可能造成提示注入。

### 3. [minecraft-mcp-server](https://github.com/yuniko-software/minecraft-mcp-server)：把 MC 变成 agent 的工具

这是 Mineflayer 的 MCP 封装。

适合你已经有一个支持 MCP 的 agent，希望直接让它观察、移动、操作 MC。它是**控制桥梁**，不是自带完整自主玩家逻辑。

**与 Mindcraft 的区别：**
- Mindcraft：使用项目现成的 agent 系统。
- Minecraft MCP：把游戏接到你已有的 agent 系统里。

### 4. [Voyager](https://github.com/MineDojo/Voyager)：经典研究实现

核心是：

- 自动生成探索目标；
- 生成代码技能；
- 根据环境反馈纠错；
- 把成功技能存进技能库，后续复用。

**很值得学习其设计，但不作为第一安装推荐。** 它是较早的研究实现，原始模型和依赖配置需要重新审视，不能把论文效果直接等同于当前开箱体验。

## 二、二游收菜：已有执行器很丰富，LLM 桥梁也开始成熟

这里最重要的判断是：

> **目前成熟的二游“收菜”方案，大多数仍然是 CV／OCR＋状态机或固定流程，不是 LLM 在实时理解游戏并自主操作。**

不过，把这些执行器接给 agent，往往比让 VLM 从零逐步点击更实用。

### 1. 两个直接面向 agent 的桥梁

| 项目 | 控制方式 | 能给 agent 什么 | 边界 |
|---|---|---|---|
| [MaaMCP](https://github.com/MAA-AI/MaaMCP) | MCP；Android ADB、Windows 窗口控制 | OCR、截图、点击、滑动、按键，以及 Pipeline 保存、加载、运行 | 不自带所有游戏的日常流程 |
| [maafw-cli](https://github.com/otowa-kotori/maafw-cli) | CLI＋AI skill；Android／Win32 | JSON 输出、截图、OCR／模板等识别、元素引用点击、多会话 | README 明确标注早期实验性，接口可能变化 |
| [MaaFramework](https://github.com/MaaXYZ/MaaFramework) | 自动化框架、多语言绑定 | 图像识别、控制器、JSON Pipeline | 是执行底座，不是 LLM agent |

**MaaMCP 是这次调研里与你需求最贴近的项目之一。**

它不仅是“截图＋点击”，还明确提供：

- `get_pipeline_protocol`
- `save_pipeline`
- `load_pipeline`
- `run_pipeline`

因此可以实现一种很有价值的流程：

> **agent 探索操作 → 生成 Pipeline → 执行验证 → 失败修正 → 后续确定性复用。**

这比每天都让模型重新理解几十张截图更合理。

另外，MaaMCP 的 Windows 后台控制并不意味着所有游戏都能最小化运行：最小化不支持，部分应用仍需要前台。**MaaFramework 生态资源也不能默认全部直接兼容或无缝调用。**

### 2. 已有游戏日常执行器

下面这些都值得作为 agent 的“技能后端”，但**不能直接归类为原生 LLM 玩家**。

| 游戏 | 开源项目 | 已有能力概览 |
|---|---|---|
| 明日方舟 | [MaaAssistantArknights／MAA](https://github.com/MAAassistantArknights/MaaAssistantArknights) | 刷理智、基建换班、信用相关、日常领取、肉鸽等；有库接口可进一步包装 |
| 原神 | [BetterGI](https://github.com/babalae/better-genshin-impact) | Windows 图像识别＋键鼠；日常一条龙、领奖派遣、刷秘境、采集路线、钓鱼等 |
| 崩坏：星穹铁道 | [March7thAssistant](https://github.com/moesnow/March7thAssistant) | 清体力、每日实训、委托、领奖及部分周常；包含云星铁相关支持 |
| 崩坏：星穹铁道 | [StarRailOneDragon](https://github.com/OneDragon-Anything/StarRailOneDragon) | 日常、刷本、领奖、模拟宇宙、小地图锄地等，可作为另一条路线 |
| 绝区零 | [ZenlessZoneZero-OneDragon](https://github.com/OneDragon-Anything/ZenlessZoneZero-OneDragon) | 影像店、刮刮乐、咖啡、材料及奖励日常；还有自动战斗和空洞相关流程 |
| 碧蓝航线 | [AzurLaneAutoScript／ALAS](https://github.com/LmeSzinc/AzurLaneAutoScript) | Python 图像识别、调度和 GUI，偏长期挂机与日常自动化 |

| 少女前线 2：追放 | [MaaGF2Exilium](https://github.com/DarkLingYun/MaaGF2Exilium) | 体力清理、派遣调度、日常领奖、商店等；部分 PC 功能尚未适配 |

**不是只有多年以前的老仓库。** 核查时 Release 页面可见：

- MAA：`v6.20.1`，2026-10-20

## 三、MC 和二游之外，还有哪些值得看？

### 原生 LLM／视觉 agent 框架

| 项目 | 游戏／方向 | 技术路线与价值 |
|---|---|---|
| [Factorio Learning Environment／FLE](https://github.com/JackHopkins/factorio-learning-environment) | 异星工厂 | 专为开发评测 LLM agent；模型生成 Python 程序，通过 REPL 执行并读取反馈。适合资源管理、生产链、长期规划，也有 MCP 可选组件 |
| [Cradle](https://github.com/BAAI-Agents/Cradle) | 荒野大镖客 2、星露谷物语、城市：天际线、Dealer’s Life 2 等 | 截图输入、键鼠输出，带规划、记忆、反思和技能机制。新游戏需要适配，不是任意游戏安装即玩 |
| [BALROG](https://github.com/balrog-ai/BALROG) | 多种游戏环境的 LLM／VLM 评测 | 更适合比较模型和 agent 策略，不是面向日常挂机的产品 |

其中 **FLE 特别值得关注**：它把游戏变成可编程环境，让模型做高层规划，比纯视觉点击容易形成可检验、可复用的行为。

### 游戏 API／模拟器／RL 环境：可以接 agent，但不自带 LLM 脑

| 项目 | 覆盖范围 | 需要区分的地方 |
|---|---|---|
| [poke-env](https://github.com/hsahovic/poke-env) | Pokémon Showdown 对战 | 结构化回合和动作，适合自接 LLM／RL；不是宝可梦主线通关 |
| [PyBoy](https://github.com/Baekalfen/PyBoy) | Game Boy／Game Boy Color | Python 模拟器控制接口，可以做按键、帧推进等；不是现成通关 agent |
| [PokemonRedExperiments](https://github.com/PWhiddy/PokemonRedExperiments) | 宝可梦红 | PyBoy 后端的强化学习训练与 agent，**不是 LLM 项目** |
| [python-sc2](https://github.com/BurnySc2/python-sc2) | 星际争霸 2 | 结构化 bot API，适合“LLM 战略＋代码战术执行”，不适合每个实时动作都等模型 |
| [stable-retro](https://github.com/Farama-Foundation/stable-retro) / [ViZDoom](https://github.com/Farama-Foundation/ViZDoom) | 复古模拟器游戏／Doom | 主要是 Gymnasium／RL 环境，需要自己加入模型和 agent 循环 |

## 四、如果你想做自己的方案，我建议怎么搭？

### 场景 A：让 agent 真正自主玩一个游戏

优先选择**结构化接口**：

1. **MC：Mindcraft，或 Mineflayer＋自己的 agent。**
2. **异星工厂：FLE。**
3. 回合制对战：poke-env。

它们能降低视觉识别误差，也更容易追踪“模型想做什么、实际做了什么、失败在哪里”。

### 场景 B：让 agent 管理多个二游的日常

优先采用：

```text
LLM agent
  理解目标、选择任务、处理异常
        ↓ MCP / CLI / 自行封装的高层工具
游戏专用执行器
  OCR、状态机、寻路、战斗与日常流程
        ↓
游戏
        ↓
状态、进度、错误截图返回 agent
```

比如自行封装 `run_daily`、`get_status`、`pause`、`collect_rewards` 这类高层工具——**这是建议的接口设计，不是上述项目都已有这些接口。**

只在流程没覆盖、界面变化或异常时，让视觉 agent 接管；成功后再固化为脚本或 Pipeline。

**不推荐的方式：** 每天让 VLM 从头观察、逐个按钮点击。成本、延迟、重复性和误操作风险都较高，战斗场景尤其如此。

## 我的最终判断

- **“自主玩 MC”已经有比较完整的开源栈：Mineflayer → Mindcraft／MCP。**
- **“二游收菜”执行器非常丰富，最现实的路线是 agent 调度它们，而不是重写成全视觉自主玩家。**
- **MaaMCP／maafw-cli 是把 coding agent 与游戏自动化连接起来的重点方向。**
- **跨任意游戏、无需适配、稳定自主游玩的通用开源方案，目前不能把它当作成熟能力。**

最后，第三方自动化可能违反游戏条款，**纯视觉或不读写内存也不代表没有封号风险**。接 agent 时应把抽卡、付费货币消费、装备分解等动作默认禁用或要求确认；游戏／ROM、模型 API 成本及各仓库 GPL／AGPL 等许可也需分别核查。
